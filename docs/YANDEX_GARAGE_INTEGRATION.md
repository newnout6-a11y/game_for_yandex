# Roadster: облачный гараж и безопасная граница платежей

Дата проверки: 18 октября 2026 года. Реализация: `src/platform-services.js`. Контрактные проверки: `tests/platform-services.test.mjs`.

## Статус поставки

- Бесплатный гараж, локальный профиль, очередь гостевых облачных сохранений и явный вход через Яндекс ID поддержаны адаптером.
- В текущей сборке реальные покупки **выключены**: `src/main.js` не передаёт `commerceConfig` или `trustedBackend`, а представление получает `payments: false`. Здесь нет платежного секрета, реального appId, сервера, договора, подключения консоли, тестового бесплатного товара или подмены успешной оплаты.
- Поддержка подписанных платежей является интеграционным каркасом. Работа реального каталога, серверной экономики и восстановления на двух устройствах должна быть проверена отдельно в настоящем draft. Unit-тесты не доказывают прохождение модерации.
- Старые ключи `aerokrai.profile.v2` и облачный `aerokraiGarageV2` сохраняются для совместимости. Прежнее бренд-предложение отклонено, точное выбранное пользователем название — **Roadster**. Эти ключи не являются названием игры и не подтверждают права на новое имя.
- Облако сохраняет существующий профиль: бесплатный Rocket, заработанные машины/косметику/исследования, результаты и прогресс. Оно не добавляет шестую вкладку: в UI пять разделов, сравнение конфигураций находится в «Инженерии», рекорды и общие показатели — в свёрнутой детали результатов.

## Публичный интерфейс

```js
const platform = createPlatformServices({
  sdk,                     // существующий createSdk()
  lifecycle,               // существующий createLifecycle()
  profileStore,            // существующий createProgressionStorage()
  onState: renderStatus,   // получает отдельную копию состояния
  // commerceConfig и trustedBackend намеренно не задаются в обычной сборке
});

await platform.init();
platform.getState();
platform.queueSave();                       // после успешного изменения progression
await platform.flush();                     // запросить серверное подтверждение
await platform.authorize({ userInitiated: true });
await platform.resolveCloudConflict('local'); // только осознанный выбор игрока
await platform.resolveCloudConflict('cloud');
await platform.retryCloud();                // повторное чтение после сетевого сбоя
// Только будущая явно настроенная денежная интеграция, не текущий UI:
await platform.catalog();
await platform.purchase(productId);
await platform.recoverPurchases();
platform.dispose();
```

`queueSave(snapshot = profileStore.get(), { durable = true })` возвращает текущее состояние очереди синхронно, а не обещание серверной доставки. Переданный snapshot должен совпадать с текущим проверенным профилем. Локальный коммит выполняет `profileStore`, не облачная очередь.

`flush()` возвращает результат конкретной попытки. При лимите, конфликте или еще неопределенном старом запросе результат остается `queued`, `rate-limited`, `conflict` или `uncertain`. Нельзя показывать «Сохранено» только потому, что Promise завершился.

`retryCloud()` сначала повторно получает Player и читает данные. Ошибка чтения не превращается в разрешение перезаписать неизвестное сохранение.

## Состояние для интерфейса

```js
{
  mode: 'yandex' | 'local-preview',
  ready: boolean,
  lang: string,
  identity: null | { id: string, authorized: boolean },
  auth: 'unavailable' | 'guest' | 'authorized' | 'pending',
  generation: number,
  local: { localSaved, readOnly, error, /* статус progression-storage */ },
  cloud: {
    available: boolean,
    status: string,
    durableRevision: number | null,
    queuedRevision: number | null,
    error: string | null
  },
  conflict: null | { reason, source, accountId, local, cloud },
  commerce: { available, status, reason, products, busy, pending }
}
```

Рекомендуемые значения статуса:

| Значение | Честный смысл |
| --- | --- |
| `unavailable` | SDK/облачного сервиса нет; локальный статус показывается отдельно |
| `loading`, `frozen` | Данные аккаунта еще не установлены; фоновые записи запрещены |
| `loaded` | Прочитан облачный снимок; это не подтверждение новой записи |
| `queued`, `saving`, `rate-limited` | Есть неподтвержденные изменения |
| `durable` | SDK подтвердил `setData(..., true)` для `durableRevision` |
| `server-durable` | Проверенный backend подтвердил каноническую экономику; это не ответ SDK setData |
| `conflict` | Нужен явный выбор двух снимков; валюты не объединяются |
| `uncertain` | Старый запрос еще может исполниться; нельзя считать его отмененным |
| `error` | Сохранение или чтение не подтверждено; локальная игра остается доступной |

`getState()` не содержит signed Player proof, платежных подписей, purchaseToken или серверной сессии. Не добавляйте их в аналитику, UI, localStorage или журналы ошибок.

## Гость, вход и конфликты

`init()` не вызывает окно входа. Гость получает Player и облако наравне с вошедшим игроком. Для входа нужен отдельный понятный CTA, например «Войти с Яндекс ID, чтобы продолжать на другом устройстве». Вызывать `authorize({ userInitiated: true })` только непосредственно в обработчике такого действия. Отказ не блокирует основной игровой цикл.

При первом чтении:

1. Совпадающие нормализованные снимки принимаются без слияния.
2. Совершенно нетронутый стартовый профиль можно заменить настоящим облачным: заработанный прогресс отсутствует.
3. Различающиеся существующие профили сохраняются в `state.conflict.local` и `.cloud` до решения игрока.
4. Старый локальный прогресс при пустом облаке также требует выбора. Иначе локальный профиль прежнего аккаунта мог бы незаметно попасть в новый.
5. Поврежденная/неизвестная версия облака не перезаписывается. Ошибка и повтор чтения безопаснее необратимой «починки».

Интерфейс выбора должен показать баланс, гараж, машины и ревизию обоих снимков. «Оставить этот компьютер» означает заменить удаленный снимок целиком. «Использовать облако» означает заменить текущий локальный снимок; существующий storage пытается сохранить прежний локальный профиль резервной копией. При недоступном localStorage честно показывать отсутствие локальной копии. Никаких `max(credits)`, сложения балансов или молчаливого выбора по дате устройства.

Для конфликта с проверенным backend разрешена только его каноническая версия: локальный выбор не может переписать финансовый ledger. Игрок может не принимать замену и продолжать бесплатную локальную игру; выпуск денежных покупок требует отдельного проверенного процесса сверки обычного прогресса.

## Смена аккаунта и неопределенные запросы

- При `ACCOUNT_SELECTION_DIALOG_OPENED` очередь замораживается, добавляется причина паузы `account-selection`, поколение identity меняется.
- После закрытия заново получаются Player и облако. Старые queued-снимки не переносятся на новый аккаунт.
- После каждого асинхронного этапа проверяется поколение. Старые ответы не изменяют новый профиль и не снимают его финансовые ограничения.
- Уже вызванный SDK setData невозможно отменить. Незавершенные записи учитываются по владельцу даже после смены поколения. Возврат в тот же аккаунт не запускает новую запись поверх еще выполняющейся старой.
- Timeout записи означает неопределенность. Новая запись этому же владельцу ждет реального завершения старого Promise. После завершения записывается актуальный выбранный снимок.
- Timeout входа возвращает управление бесплатной игре, но не открывает второе окно и не разрешает писать неизвестному аккаунту.
- Timeout оплаты не считается отменой. Физический SDK-запрос остается заблокирован до настоящего завершения; пустой recovery-ответ не разрешает открыть вторую оплату, пока первый запрос еще выполняется.
- Неопределенный consume не дублируется, пока исходный SDK-запрос не завершился.

Текущий рекламный `canShow` в `src/main.js` допускает запрос только на экране результатов и если экран поворота устройства не блокирует игру; он запрещает его при `lifecycle.has('payment')`, `lifecycle.has('account-selection')`, `platform.getState().auth === 'pending'` или `platform.getState().commerce.busy`. Последний флаг остается true у еще не завершенного физического платежа даже после пользовательского timeout. События SDK pause/resume и скрытие вкладки продолжают обрабатываться общим lifecycle; закрытие оплаты не снимает `user`, `hidden`, `platform` или `ad`.

Это не обещание отсутствия рекламы до первого заезда: собственного стартового запроса нет, но платформа может показать свою стартовую рекламу. Значения трёх квалифицирующих заездов и 180 активных секунд — продуктовые настройки проекта, не официальные числовые требования Яндекса; полные правила runtime описаны в [ROADSTER_AD_POLICY](ROADSTER_AD_POLICY.md).

## Ограничения нагрузки и гарантий

Адаптер хранит только последний queued-снимок, сериализует записи и по умолчанию выдерживает минимум 3500 мс между началами записей. В скользящем окне 5 минут используются консервативные бюджеты 18 getPlayer и 90 общих getData/setData. Тестовый параметр `minSaveIntervalMs` не отключает скользящий бюджет. Профиль ограничен существующим лимитом 190000 UTF-8 байт, полный облачный пакет — 195000 байт.

SDK не дает клиенту межустройственную CAS-транзакцию. Последовательная очередь предотвращает гонки одного экземпляра приложения, но **не** доказывает exactly-once между двумя устройствами и не защищает клиентскую валюту от подмены. При конкурентной бесплатной игре на двух устройствах необходима отдельная серверная политика согласования. Browser unload также не гарантирует завершения сети; важные действия должны инициировать сохранение сразу, не только на выходе.

## Контракт будущего trustedBackend

Этот интерфейс — контракт Roadster, не API Яндекса. В коде нет его сетевой реализации.

Каталог допускается только при всех условиях:

- `commerceConfig.enabled === true`;
- реальный `commerceConfig.appId` совпадает с `ysdk.environment.app.id`;
- `commerceConfig.products` содержит точные SDK productId с `kind: 'permanent' | 'consumable'`;
- backend предоставляет методы ниже и capabilities `verifiedIdentity`, `durableLedger`, `receiptIntentBinding` со значением true;
- backend подтвердил подписанного игрока;
- `getPayments({ signed: true })` и реальный SDK-каталог успешно доступны;
- нет конфликта или неустановленного аккаунта.

Capabilities описывают обязательства разработанного сервера, а не заменяют проверку его безопасности. Один boolean не создает надежную экономику.

```ts
interface TrustedBackend {
  capabilities: {
    verifiedIdentity: true;
    durableLedger: true;
    receiptIntentBinding: true;
  };
  authenticate(input: {
    signature: string; appId: string;
  }): Promise<VerifiedSession>;
  createPurchaseIntent(input: {
    session: VerifiedSession; productId: string; appId: string;
  }): Promise<VerifiedIntent>;
  fulfillPurchase(input: {
    session: VerifiedSession; intentId: string; signature: string;
  }): Promise<Settlement | Pending>;
  reconcilePurchases(input: {
    session: VerifiedSession; signature: string;
  }): Promise<Settlement | Pending>;
}

type VerifiedSession = {
  verified: true; subjectId: string; appId: string;
  // Внутренняя сессия серверной реализации, никогда не публичное UI-state.
};
type VerifiedIntent = {
  verified: true; durable: true; subjectId: string;
  intentId: string; productId: string; developerPayload: string;
};
type Pending = { status: 'pending' };
type Settlement = {
  verified: true; durable: true; subjectId: string; appId: string;
  stateRevision: number; canonicalState: ProgressionProfileV2;
  intentId?: string; // обязателен в ответе fulfillPurchase
  transactions: Array<{
    transactionId: string; productId: string;
    kind: 'permanent' | 'consumable';
    status: 'applied' | 'already-applied';
    consume: 'required' | 'not-required' | 'already-consumed';
    purchaseToken?: string; // только проверенный сервером токен для required
  }>;
};
```

Обязательства сервера:

1. Проверить подпись Player, app и субъекта; posted playerId не является доказательством. Настроить защищенный HTTPS transport, origin/session-проверки и сроки действия сессии.
2. Создать и **надежно сохранить** одноразовый intent до вызова SDK purchase. Связать его с проверенными пользователем, товаром, приложением и серверным сроком действия. developerPayload — opaque ссылка, не цена и не право на награду.
3. Проверить подпись receipt, допустимую структуру/статус, товар, приложение, intent и владение. Документация не гарантирует, что простое соседство receipt и Player ID доказывает владельца. Неизвестные старые receipts переводить в pending, а не присваивать текущему аккаунту.
4. Одной DB-транзакцией записать unique receipt token, изменение канонической экономики и новую серверную ревизию. Повтор возвращает `already-applied` и целый канонический снимок, а не повторяемую дельту валюты.
5. Вернуть `durable: true` только после commit. Не возвращать успешную пустую сверку, пока остаются неразрешенные ранее созданные intents.
6. `reconcilePurchases` разбирает подписанный batch на сервере и сверяет незавершенные покупки/intent ledger. Подписанный результат SDK на клиенте содержит `signature`, а не обычный массив с productID/token.
7. Соблюдать монотонность `stateRevision`. Одинаковая ревизия с разным каноническим состоянием отклоняется клиентом.
8. Хранить постоянные entitlements в server ledger и возвращать `consume: 'not-required'`. Они никогда не consume. Используемые consume только после надежной выдачи; токены не могут повторяться в одном batch.
9. Реализовать проверенное согласование обычного прогресса с канонической экономикой. Нельзя принимать произвольный клиентский баланс как финансовый источник истины. Текущий адаптер **не начинает оплату**, если локальный профиль разошелся с последним подтвержденным backend-снимком: возвращает `server-progress-reconciliation-required`. До реальной реализации этой части платная витрина не включается.
10. Определить refund/revocation, сроки сезона, сохранение купленных предметов и восстановление на другом устройстве. Часы клиента не являются источником этих решений.

Клиент заменяет профиль целым проверенным canonicalState. Если изменение произошло во время запроса или первый серверный снимок расходится с локальным, сохраняются оба варианта в явном конфликте, consume не выполняется. После server commit сбой localStorage не отменяет серверную выдачу; UI продолжает честно указывать отсутствие локального сохранения.

## Проверка перед включением денег

`node --test tests/platform-services.test.mjs` проверяет локальный fallback, гостя, вход/отказ/timeout, конфликты, stale reads/writes, очередь, rate/size bounds, невозможность замаскировать queued как durable, отсутствующий localStorage, явную конфигурацию, настоящие поля цены/валюты, signed-only путь, однократную каноническую выдачу, восстановление, no-consume permanent, неопределенные платежи и смену identity во время consume.

В настоящем SDK draft отдельно проверить: гостя и вошедшего игрока; вход с выбором двух разных профилей; закрытие/перезагрузку между оплатой, commit и consume; реальное повторное восстановление на другом устройстве; currency mock; отсутствие сети; системные pause/resume; slow network; открытый платеж при смене аккаунта. Использовать выделенные тестовые аккаунты. Не включать реальные покупки лишь на основании успеха unit-тестов.

## Официальные основания

- [Player и облачные данные](https://yandex.ru/dev/games/doc/ru/sdk/sdk-player): гостевой Player, isAuthorized, явный auth dialog, signed identity и различие queued/durable setData. Там же опубликованы ограничения методов и размера данных.
- [События SDK](https://yandex.ru/dev/games/doc/ru/sdk/sdk-events): открытие/закрытие выбора игрового аккаунта, повторное получение Player, независимые платформенные pause/resume.
- [Платежи SDK](https://yandex.ru/dev/games/doc/ru/sdk/sdk-purchases): signed-ответы, серверная проверка, каталог/валюта, восстановление, различие постоянных и используемых товаров, выдача до consume.

Эти ссылки подтверждают платформенные механизмы. Архитектура очереди, conflict UI, лимиты с запасом и контракт собственного backend — решения проекта, а не дополнительные требования Яндекса.
