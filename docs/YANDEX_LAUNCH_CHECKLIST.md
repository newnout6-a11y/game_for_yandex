# Яндекс Игры: запуск, монетизация и выпуск автомобильной игры

Проверено 18 октября 2026 года по официальной документации. Страница полного списка требований сообщает обновление 9 октября 2026 года. Это исследование и проект интеграции, не заключение о прохождении модерации. Доступ к аккаунту разработчика, реальному каталогу, платежам и договору не проверялся.

Обозначения: **обязательно** — опубликованное требование платформы; **рекомендация Яндекса** — рекомендация документации; **решение проекта** — предлагаемый дизайн, а не правило платформы; **не установлено** — отсутствует подтвержденная спецификация.

## 1. Главные решения для релиза

1. Вход без регистрации, сразу понятная кнопка первого заезда. Не превращать каталог гаража в обязательный длинный онбординг.
2. Гостевой прогресс сохраняется. Авторизация только по отдельному понятному действию игрока с объяснением пользы; отказ не блокирует игру. Уже вошедшему игроку повторное предложение не показывать. [Требования к авторизации](https://yandex.ru/dev/games/doc/ru/requirements/1/2).
3. Никакой дополнительной полноэкранной рекламы в нашем стартовом сценарии: Яндекс уже автоматически показывает стартовый блок. Это решение проекта предотвращает двойное рекламное прерывание. Для стартового блока прямых callback нет: обрабатывать платформенные pause/resume. [События SDK](https://yandex.ru/dev/games/doc/ru/sdk/sdk-events).
4. До появления проверенного SDK-каталога и надежных облачных сохранений платная витрина неактивна. Игровые кредиты можно тратить на машины/детали независимо от реальных платежей.
5. Пользовательская обложка с Tesla Roadster остается предметом проверки прав до публичного коммерческого выпуска. Отсутствие заявления о сотрудничестве не заменяет права на модель, имя, изображения и логотипы.

## 3. Предлагаемый первый вход

Это продуктовый сценарий, не предписанный Яндексом макет.

1. **Boot:** легкая фирменная иллюстрация и реальный индикатор загрузки. Загружаются SDK, язык, базовая сцена и сохранение. Реклама/магазин не блокируют получение бесплатного стартового автомобиля.
2. **Ready:** интерактивный экран «Первый заезд» / «Продолжить», выбранная бесплатная машина, настройки звука. Позади может быть спокойная оригинальная 3D-презентация. Здесь отправляется Game Ready.
3. **Первый заезд:** короткая обучающая дистанция, одна подсказка за раз, без нашего interstitial. Не нужно показывать сразу шесть разделов гаража.
4. **Результат:** сначала честно начислить и сохранить базовую награду. Рядом необязательное предложение «Посмотреть рекламу: +… кредитов». «В гараж» и «Еще заезд» доступны без видео.
5. **Гараж:** первое осмысленное улучшение, затем полный каталог. Авторизация предлагается ненавязчиво: «Войти с Яндекс ID, чтобы продолжать на другом устройстве»; кнопка «Не сейчас».

Предлагаемые параметры скорости: первое взаимодействие важнее тяжелого showroom; остальные модели подгружаются по необходимости. Это не означает ранний Ready поверх незавершенного экрана. У debug-панели Game Ready есть 90-секундный timeout, но 90 секунд не следует превращать в целевое время загрузки. [Debug-панель](https://yandex.ru/dev/games/doc/ru/console/debug-panel).

## 4. Реклама: допустимые места и ограничения

Официальные правила: в коротком real-time уровне (<5 минут) нельзя вставлять interstitial внутрь движения. Между пользовательским неигровым действием и рекламой допустимо не более 2 секунд. Для длинных real-time уровней возможна реклама по таймеру, но с уже остановленной игрой и заметным предупреждением на 2 секунды. Частоту fullscreen регулирует платформа. Эти правила не задают универсального обязательного интервала «180 секунд». [Расположение рекламы](https://yandex.ru/dev/games/doc/ru/requirements/4/4).

**Решение проекта:** в гонке не использовать mid-race interstitial даже для длинной трассы. Единственный initial placement — подтвержденный переход с результата в гараж/следующий заезд. Первую обучающую гонку исключить, затем использовать собственный мягкий cooldown и проверять влияние на завершение сессии. Не ставить рекламу на каждое перелистывание каталога. Не показывать два рекламных формата подряд после rewarded.

Rewarded SDK не имеет опубликованного лимита частоты вызова. Вознаграждение выдавать только через `onRewarded`; закрытие или `onError` не равны заработанной награде. `onClose(wasShown)` у fullscreen может приходить и когда блок фактически не показывался. Sticky управляется через SDK при соответствующей настройке консоли; по умолчанию включенный баннер может появляться на старте. [Рекламный API](https://yandex.ru/dev/games/doc/ru/sdk/sdk-adv).

**Решение проекта для RV:** дополнительная выплата за завершенный заезд или тест-драйв машины на один заезд, если это не закрывает базовый контент. Не продавать безопасность, обязательный ремонт, топливо для продолжения, сохранение уже заработанного рекорда. Тест-драйв не должен попадать в соревновательные рекорды, если машина/буст изменяют баланс. Ни `no-fill`, ни отмена не должны списывать кредит или замораживать интерфейс.

**Отключение рекламы:** без ограничения в описании покупка должна отключить игровые fullscreen и sticky. Яндекс отдельно допускает сохранение принудительного стартового блока платформы и добровольных RV. Формулировать предложение точно, например «Убирает межзаездную рекламу и баннеры в этой игре; добровольные видео с бонусом остаются. Стартовая реклама Яндекса управляется платформой». Не обещать отключить то, чем игра не управляет. [Проверка no-ads](https://yandex.ru/dev/games/doc/ru/requirements/1/13).

## 5. Покупки, восстановление и сезонный пропуск

### Подтвержденный контракт SDK

`getPayments()` или `getPayments({signed:false})` предоставляет `getCatalog()`, `purchase({id, developerPayload?})`, `getPurchases()`, `consumePurchase(token)`. В обычном режиме receipt содержит `productID`, `purchaseToken`, `developerPayload`. При `signed:true` purchase/getPurchases возвращают `{signature}`, а не тот же объект receipt. Подпись HMAC с данными в base64 должна проверяться вашим сервером; секрет никогда не хранится в клиенте. Постоянные покупки восстанавливаются из getPurchases и не консумируются. Используемые: сначала начислить и сохранить, затем consume; после consume запись необратимо удаляется. Незавершенные покупки проверяются повторно, в том числе при запуске. [Платежный SDK](https://yandex.ru/dev/games/doc/ru/sdk/sdk-purchases).

Название, описание, цена и изображение валюты приходят из каталога, включая `price`, `priceValue`, `priceCurrencyCode`, `getPriceCurrencyImage()`. Интерфейс обязан пройти currency mock, а не всегда писать «яны»/«рубли». [Проверка валюты](https://yandex.ru/dev/games/doc/ru/requirements/1/13).

Консоль допускает до 500 товаров; иконка товара 256×256 PNG; описание до 200 символов; обязательны RU/EN тексты. Реальная активация зависит от статуса сотрудничества/подключения. При активной единой лицензионной схеме покупки подключаются автоматически; иначе существует отдельная процедура. Исследование не подтверждает текущий статус пользователя. [Консоль IAP](https://yandex.ru/dev/games/doc/ru/console/purchases).

### Решения проекта

- **До backend:** не называть localStorage кошельком с гарантированным восстановлением. Выпустить рекламную модель, а реальные платные кнопки держать выключенными до полной проверки.
- **Permanent:** автомобиль/косметический набор или no-ads со стабильным product mapping. Если предмет есть в каталоге, но локального обработчика нет, не продавать его и не потреблять неизвестный receipt.
- **Consumable:** пакеты игровой валюты только с token-ledger и восстановлением. Платформа оплаты не заменяет транзакционность нашей экономики.
- **Сезон:** один конкретный сезон — одна разовая покупка, без автоматического продления. Заранее видны начало/конец в UTC, доступные награды, необходимые действия и правила поздней покупки/получения. Сохранять seasonId и claim-ledger; не уничтожать купленные косметические предметы в конце сезона. Старые productId нельзя переиспользовать для нового сезона.
- **Честная продажа:** показывать, какие премиальные награды уже заработаны и будут доступны сразу; не рекламировать оставшийся срок без проверенного времени. Если срок закончился во время платежного окна, обработка должна выдать заранее заявленный результат либо уйти в проверяемое обращение, но не молча потерять оплату.

**Не установлено:** в изученных актуальных Games SDK/requirements нет отдельного сезонного API, документированной автоподписки, универсального числового ограничения длительности пропуска либо JS API для возврата/отзыва покупок. Это не доказательство юридического отсутствия ограничений. Перед продажей ограниченного по сроку пропуска подтвердить условия с поддержкой и текущим договором. Метрики консоли показывают возвраты и позволяют искать транзакции по purchaseToken, но это не спецификация webhook/автоматического отзыва. [Метрики покупок](https://yandex.ru/dev/games/doc/ru/console/purchase-metrics).

Для календарных механик существует `ysdk.serverTime()` в миллисекундах: использовать его вместо часов устройства. Он помогает против изменения системного времени, но клиентская функция не заменяет серверную авторитетность экономики. [Серверное время](https://yandex.ru/dev/games/doc/ru/sdk/sdk-server-time).

## 6. Сохранение и смена аккаунта

SDK поддерживает Player для гостя; `isAuthorized()` — актуальный способ проверки, `getMode()` устарел. Лимиты: getPlayer 20 запросов/5 минут; getData/setData 100/5 минут; setData до 200 КБ. Stats до 10 КБ, 60 запросов/минуту. У `setData(data,false)` успешный Promise означает проверенные/поставленные в очередь данные, а не доставку серверу; критические сохранения должны дожидаться `setData(data,true)`. Для собственного домена safeStorage доступен через getStorage; архивный SDK делает браузерное хранилище надежнее автоматически. [Данные игрока](https://yandex.ru/dev/games/doc/ru/sdk/sdk-player).

При входе после гостевой игры платформа может показать выбор двух прогрессов. Использовать `ACCOUNT_SELECTION_DIALOG_OPENED` / `ACCOUNT_SELECTION_DIALOG_CLOSED`: остановить фоновую запись, затем заново получить Player и его данные. Не перезаписывать выбранный аккаунт старой локальной очередью. SDK pause/resume также охватывает платежное окно, скрытие вкладки и сворачивание; его разметка не должна запускать ранее остановленный из-за меню gameplay. [События](https://yandex.ru/dev/games/doc/ru/sdk/sdk-events).

**Предлагаемая модель:** schemaVersion, accountId, saveRevision, garage, currencies, upgrades, contracts, seasonClaims, processedReceipts, settings. Записи делаются последовательной очередью; отделить телеметрию заезда от финансового состояния. Миграция старого локального формата — резервная копия плюс проверка схемы, а не очистка. Не складывать балансы двух сохранений и не брать «максимум валюты»: это создает дублирование. Если нельзя уверенно решить конфликт без потери, оставить оба снимка и дать осознанный выбор.

**Ограничение безопасности:** документация setData не обещает CAS, атомарные multi-device transactions или защиту клиентского состояния от подмены. Token-ledger в одном облачном снимке снижает риск повтора, но не дает строгой гарантии exactly-once между двумя устройствами. Для платной развивающейся экономики нужен серверный transaction ledger: проверенный receipt → атомарно reward + unique token → подтвержденное сохранение → consume. При сбое consume повторяется, reward повторно не начисляется. При сбое сохранения receipt не consume.

## 7. Рекомендуемый интерфейс адаптера

Это проект интерфейса приложения, не названия новых методов SDK.

```ts
type PlatformMode = 'yandex' | 'local-preview';
type PurchaseResult =
  | { status: 'fulfilled'; transactionId: string }
  | { status: 'pending'; reason: string }
  | { status: 'cancelled' | 'unavailable' | 'error'; reason?: string };

interface PlatformAdapter {
  init(): Promise<{ mode: PlatformMode; lang: string; cloud: boolean; payments: boolean }>;
  markReady(): void;
  setGameplayActive(active: boolean): void;
  onPlatformPause(callback: (paused: boolean) => void): () => void;
  getIdentity(): Promise<{ id: string; authorized: boolean }>;
  authorizeFromExplicitUserAction(): Promise<'authorized' | 'cancelled' | 'error'>;
  loadProgress(): Promise<LoadResult>;
  saveProgress(snapshot: Save, options: { durable: boolean }): Promise<SaveResult>;
  onAccountSelection(callback: (phase: 'open' | 'closed') => void): () => void;
  showRewarded(placement: RewardPlacement): Promise<'rewarded' | 'closed' | 'unavailable' | 'error'>;
  showInterstitial(placement: BetweenRacePlacement): Promise<'shown' | 'not-shown' | 'error'>;
  loadCatalog(): Promise<VerifiedCatalog>;
  purchase(productId: VerifiedProductId): Promise<PurchaseResult>;
  reconcilePurchases(): Promise<ReconciliationResult>;
  serverNow(): { milliseconds: number; trustedSource: boolean };
}
```

Инварианты реализации:

- Одна активная рекламная/платежная операция, защита от двойного клика.
- Reward callback имеет operationId и однократный commit; close не выдает награду.
- Возврат управления идемпотентен при комбинациях onError/onClose/platform resume.
- Pause хранит набор причин: menu, user, ad, payment, hidden, platform, account-selection. Размораживание только при пустом наборе и фактически активном заезде. Сбрасывать нажатые педали/клавиши при остановке.
- Покупка требует подтвержденного productId из свежего каталога, готовой выдачи и надежного сохранения. Нет SDK — unavailable, а не mock success.
- Не помечать платеж canceled, если деньги могли списаться: статус pending и reconciliation.
- На локальном preview любая демонстрация платежа явно маркирована; не переносить mock entitlements в настоящее облако. Release build не содержит dev-свитча бесплатной выдачи.
- При смене identity старые сохранения/операции нельзя применить к новому accountId.
- HMAC проверяется на сервере constant-time сравнением; token uniqueness хранится в БД; developerPayload не считается доказательством прав или цены. Секреты, signatures, purchaseToken не уходят в клиентские аналитические события.

### Строгий контракт собственного backend для будущей реализации

Следующие маршруты и поля предлагаются проектом и **не являются API Яндекса**:

```ts
// Authenticated HTTPS session established by server-side verification
// of the Yandex signed Player identity, not by trusting a posted playerId.
type PurchaseIntent = {
  intentId: string;       // server-generated, single-use nonce
  productId: string;      // approved server catalog ID
  expiresAt: number;
  developerPayload: string; // opaque reference to this intent
};

type FulfillmentResponse =
  | {
      status: 'applied' | 'already-applied';
      transactionId: string;
      subjectId: string;
      productId: string;
      stateRevision: number;
      canonicalState: EconomyState;
      consume: 'required' | 'not-required' | 'already-consumed';
    }
  | { status: 'pending'; transactionId: string; retryAfterMs: number }
  | { status: 'rejected'; code: string };
```

Предлагаемый flow: create intent по проверенной серверной сессии → SDK purchase с opaque developerPayload → fulfillment передает только signature и intentId → сервер проверяет HMAC, форму данных, принадлежность приложению, соответствие product, intent/account и повтор token → одна DB-транзакция меняет экономику и receipt ledger → возвращает canonical state. Клиент никогда не присылает авторитетные amount, price, tier или award. Applied и already-applied заменяют snapshot на canonical state, а не повторно прибавляют дельту.

**Граница доверия:** опубликованный пример signed receipt сам по себе не документирует полноценную привязку покупки к текущему Player ID. Нельзя объявлять владение подтвержденным лишь потому, что клиент прислал рядом два значения. Проект intent с подписанным payload должен быть проверен на реальном SDK, включая восстановление и смену guest/account; неизвестные старые receipts отправляются на reconciliation, а не произвольно закрепляются за текущим пользователем. Нет надежно подтвержденного владения — нет выдачи и consume. Refund/revocation требуют отдельного подтвержденного процесса, не выдуманного callback.

На ACCOUNT_SELECTION_DIALOG_OPENED: запретить новые purchase intents, остановить save writer, пометить поколение identity устаревшим. На CLOSED: заново получить Player и подтвержденную сессию, загрузить canonical progress, применить только ответы этого поколения. Старую незавершенную оплату не отменять логически и не забывать; сохранить ее как pending для владельца intent до корректной сверки.

## 8. Минимальная приемка перед заявкой

| Тест | Ожидаемый результат |
|---|---|
| Чистый гость → первый заезд → перезагрузка | Та же машина, баланс, контракт, рекорд; нет навязанного входа |
| SDK отсутствует / отклонен | Бесплатная игра доступна в preview, реальные реклама/покупки недоступны честно |
| SDK медленный, cloud timeout | Нет вечного загрузчика или ложного «Сохранено в облаке»; платная выдача не теряется |
| Launch ad | Нет нашей второй рекламы; заезд/звук не идут под платформенным блоком |
| Меню → ad → close; user pause → hidden → visible | Игра не возобновляется сама при оставшейся причине паузы |
| RV close/error/no-fill/onRewarded twice | Ноль наград без reward; ровно одна с reward; UI снова доступен |
| Fullscreen wasShown=false | Нормальный переход продолжается, без зависания и ложной метрики показа |
| Двойной клик покупки | Одна операция; кнопка защищена до терминального результата |
| Сбой после оплаты, до сохранения | Receipt остается recoverable, выдача восстанавливается |
| Сбой после сохранения, до consume | Receipt обрабатывается без второй выдачи |
| Второе устройство / браузер | Entitlements и прогресс доступны тому же аккаунту |
| Гость → вход → выбор старого аккаунта | Очередь гостя не затирает выбранные данные |
| Перевод / currency mock | UI берет SDK lang при старте; цена и иконка валюты меняются из SDK |
| Mobile landscape/portrait, zoom 80–125%, sticky show/hide | Не теряется прогресс, нет системного scroll/refresh, кнопки видны |
| Один палец, keyboard RU/EN | Старт, управление и финиш достижимы без второй руки/смены раскладки |
| Изменение часов устройства, конец сезона во время оплаты | Таймер и выдача следуют определенной политике, а не Date.now() |
| Release ZIP | Размер/пути корректны, нет dev mock, неработающих CTA, внешней оплаты |

Тестировать в реальном draft и debug-panel: loader IT, Ready, I18N, pause/play, network throttling, currency mock. Локальные mocks не доказывают приемку. Документация предупреждает, что при проверке рекламы в draft/prod показывается настоящая реклама: не нажимать по ней ради проверки кликов. Очистку облака и тестовые платежи проводить только на специально выделенных тестовых аккаунтах. [Debug-панель](https://yandex.ru/dev/games/doc/ru/console/debug-panel), [проверка рекламы](https://yandex.ru/dev/games/doc/ru/requirements/4/4).

## 9. Обложка, assets и бренд

Для каталога: иконка 512×512 PNG, обложка 800×470 PNG; hero для подборок 1560×520 PNG/JPG. Скриншоты 16:9 либо 9:16, длинная сторона 1280–2560, JPEG/24-bit PNG, минимум два для каждой заявленной платформы. Горизонтальное видео помечено обязательным: MP4 16:9, высота от 400, до 28 секунд/100 МБ. Параметры формы при подаче остаются конечной проверкой. Одноориентационный mobile draft использует SDK-заглушку при неправильном повороте. [Поля черновика](https://yandex.ru/dev/games/doc/ru/console/add-new-game/draft).

Не использовать скриншот как cover/icon; для них сделать отдельную композицию. Скриншоты должны показывать реальную игру, а не нарисованный будущий гараж. Не имитировать рейтинг/бейджи Яндекса и не добавлять системные статус-бары. Game UI допустим в скриншотах, не в cover/icon. [Медиаматериалы](https://yandex.ru/dev/games/doc/ru/requirements/8/3/4).

Tesla заявляет авторские права на материалы своего сайта, торговые права на модельные имена и знаки и отсутствие автоматически выдаваемой лицензии. Поэтому изображение с сайта Tesla нельзя считать свободным маркетинговым ассетом. [Tesla IP](https://www.tesla.com/legal/additional-resources?redirect=no).

**Решение проекта:** для свободного выпуска использовать собственный вымышленный электрический родстер с отличимым дизайном и собственным именем; либо документировать разрешение на конкретные брендовые материалы и коммерческое распространение. Не создавать ложного впечатления официальной игры Tesla. Независимый disclaimer полезен для ясности, но не гарантирует законности. Лицензия стороннего 3D-ассета на mesh может не охватывать автомобильный бренд. Собрать rights ledger: источник, автор, лицензия, коммерческое использование, модификация, redistribution, trademark scope. Модерация Яндекса не подтверждает юридическую чистоту материалов. [Полный список, примечание и 3.5](https://yandex.ru/dev/games/doc/ru/concepts/requirements).
